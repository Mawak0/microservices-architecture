# Архитектура сервиса приёма

Сервис реализует контракт 0.3: фиксирует один приём на зарегистрированный бланк,
сохраняет проверенный снимок и публикует надёжные события. Задачи, допуск команд,
разрешение поздней сдачи и пользовательские роли приходят от внешних владельцев.
Он не получает эталоны и не вычисляет баллы.

## Направление зависимостей

```text
Api (HTTP, авторизация, composition root)
  ├── Application (сценарии, порты)
  └── Infrastructure (реализации портов)
         └── Application
                └── Domain (агрегаты и инварианты, только BCL)
```

У Domain нет ссылок на другие проекты или пакеты. Application ссылается только
на Domain. Обе сборки обходятся без JSON, ASP.NET, HttpClient, PostgreSQL, DI и IO.
Фактические сборочные ссылки, csproj и исходники проверяются архитектурными тестами.
API использует Infrastructure только в Composition.cs и Program.cs при сборке приложения.

## Агрегаты и сценарии

`IntakeSession` защищает переходы open/closed, неизменную идентичность игры,
монотонную версию разрешения и исключающую границу дедлайна. `Receipt` неизменяем
после успешного приёма и содержит точную принадлежность бланка и ссылку на снимок.
`Admission` и `TeamAdmission` проверяют применимость внешних разрешений.
Публичных сеттеров у агрегатов нет. Новые типы игр не требуют switch по их именам.

Отдельные классы Application выполняют SynchronizeIntake, CloseIntake,
AcceptBlank, SubmissionFinalizer, GetReceipt, GetIntakeSession,
RecoverPendingSubmission и DeliverPendingEvent. Каждый класс имеет одну причину
изменения. Узкие порты отделяют реестр бланков, допуск команды, игру, декодер QR,
изображения, часы, идентификацию, доставку событий и конкретные репозитории.
Порт unit of work ограничивает короткую атомарную операцию; HTTP вызовы находятся
за её пределами. В Infrastructure нет универсального бизнес-диспетчера.

SRP соблюдается разделением агрегатов, сценариев и адаптеров. OCP обеспечивают
заменяемые порты и конфигурация типа игры. LSP проверяется контрактом порта и
тестами поведения HTTP/PostgreSQL адаптеров; ошибки не заменяются фиктивным успехом.
ISP выражен предметными интерфейсами вместо одного внешнего gateway/store.
DIP обеспечивается зависимостью ядра от собственных портов: внешние библиотеки
реализуют эти порты и подключаются только composition root. Интерфейс на каждый
сценарий не добавлен: независимой заменяемой границы у такого интерфейса не было бы.

## Сохранение и восстановление

1. Сервер декодирует настоящий PNG/JPEG через SkiaSharp и ZXing. Ровно один
   читаемый QR должен совпасть с клиентским token; затем доверенный реестр
   подтверждает подпись/принадлежность. Несколько QR считаются неоднозначными.
2. Короткая PostgreSQL-транзакция резервирует уникальный blankId, receiptId и
   (scope, Idempotency-Key), сохраняя именно проверенные байты. Другая заявка
   на тот же бланк получает конфликт. Одновременный повтор того же ключа ждёт
   результат первоначальной операции, затем получает её квитанцию.
3. HTTP-хранилище сохраняет эти же байты с receiptId как идемпотентным ключом.
   После сохранения заново читаются допуск команды, разрешение игры и время.
4. Финальная транзакция проверяет актуальный сеанс и владельца резервирования,
   сохраняет Receipt, результат идемпотентности и ReceiptAccepted в outbox,
   затем удаляет резервирование. Только после commit возвращается 201.

Момент приёма — окончательная фиксация после загрузки. Загрузка, начатая до
дедлайна, но законченная после него, отклоняется, если поздняя сдача не разрешена.
Закрытие во время незавершённой загрузки исключает её из manifest, а finalizer
не может принять ответ в закрытый сеанс. Manifest включает все уже подтверждённые
ответы, даже если события ещё не доставлены. При поздней сдаче старые квитанции
и ограничения уникальности сохраняются.

На явный отказ хранилища резервирование удаляется: бланк можно подать снова.
При crash, отмене клиента или неопределённом временном сбое проверенные байты
остаются в журнале. Worker после истечения 30-секундной аренды возобновляет
загрузку с тем же receiptId. Истёкшее разрешение/отзыв допуска прекращает такой
приём. Данные принятых снимков также остаются в PostgreSQL для восстановления и
проверки целостности хранения.

Outbox хранит точный конверт и стабильный eventId. Worker резервирует запись
транзакцией, публикует вне неё и помечает доставленной только после успеха.
Неопределённый результат сети или restart означает повтор того же сообщения,
а не новый eventId; потребитель обязан дедуплицировать eventId.
Устаревший worker не может подтвердить запись, переданную другому worker.
PostgreSQL WAL, транзакции BEGIN IMMEDIATE и ограничения UNIQUE являются механизмом
согласованности; общего process-wide mutex нет.

## Конкретные границы развёртывания

Поставщик идентификации, владелец игры/команды, реестр материалов, защищённое
хранилище изображений и HTTP-приёмник событий должны быть настроены.
Подлинность QR проверяет реестр материалов; серверный декодер проверяет снимок,
а не создаёт собственную систему подписи. В API нет тестовых имён токенов.
Внешние часы доступны исключительно в окружении ContractTests.

Между отдельным HTTP-хранилищем и PostgreSQL невозможна общая транзакция.
При сохранении изображения перед окончательным отказом могут остаться
неиспользуемые объекты; хранилищу нужна политика их уборки по receiptId.
HTTP-хранилище должно надёжно сохранять объекты и идемпотентно обрабатывать
receiptId; при потере его ответа сервис повторит upload.
Нужны резервное копирование PostgreSQL/снимков, политика хранения персональных
данных, TLS и сетевое ограничение доверенных интеграций. Эти свойства внешних
провайдеров тестовый стенд не подтверждает.

На Windows выполнены настоящие PNG/JPEG/двойной QR, PostgreSQL restart, rollback,
конкурентная сдача, отмена и повторная доставка. Linux native assets включены;
Ubuntu workflow дополнительно проверяет фактическую загрузку native runtime.
Поддержка камеры/UI остаётся отдельным заданием contracts/ui-requirements.md.
