# Заглушки внешних зависимостей (НЕ реализации сервисов)

`npm run fixtures` запускает in-memory HTTP-сервер только на loopback.
Данные исчезают при остановке. `FIXTURE_PORT` меняет порт (по умолчанию 19100).
Нельзя разворачивать этот стенд в production: тестовые управляющие маршруты
намеренно не имеют авторизации.
Один процесс заглушек обслуживает один последовательный запуск набора:
отключение транспорта событий — глобальная настройка этого процесса. Для
одновременных прогонов разных сервисов используйте разные порты/экземпляры.

Будущему сервису нужны адаптеры следующих контрактов. Названия его переменных
окружения не навязываются — адреса адаптеров настраиваются в реализации.

| Метод и путь | Назначение |
|---|---|
| `POST /auth/introspect` `{token}` | `{active,userId,roles}`; тестовый провайдер идентификации |
| `GET /games/{id}` | Расширяемый system, admissionVersion, lateSubmissionAllowed, capabilities, сроки, настройки, taskAssignments |
| `GET /teams/{id}` | Команда, допуск к игре |
| `GET /tasks/{id}` | Неизменяемая задача и эталон по точному ID (только доверенному адаптеру) |
| `GET /clock` | `{now}`; внедряемые серверные часы только для тестового режима |
| `GET /material-templates/{encodedKey}` | Декларативный шаблон; адаптер репозитория сервиса материалов |
| `POST /blank-verifications` `{qrToken}` | Проверенный бланк или 422 `INVALID_QR` (для приёма) |
| `GET /receipts/{id}` | Уже принятый ответ для восстановления доверенных данных проверки |
| `POST /images` `{receiptId,blankId,dataBase64,mediaType}` | Сохранить снимок, ответ `{imageRef}`; может вернуть 503 |
| `GET /images/{id}` | Сохранённые байты снимка |
| `POST /events` | Приёмник конвертов событий; может вернуть 503 для теста повторной доставки |

Эталоны находятся в защищённом контракте библиотеки, не в публичном API материалов.
Тестовые провайдеры не реализуют ни печать, ни приём, ни проверку, ни квоты.

Токены: `test-admin`, `test-observer`, `test-checker`, `test-checker-2`,
`test-organizer`, `test-multi` (наблюдатель + проверяющий), `test-system`
(техническая идентичность, не новая пользовательская роль).
В production должна использоваться реальная проверка доверия.

## Управление сценариями (только тестовый стенд)

- `POST /__test/scenarios` с параметрами `system`, `submissionOpen`, `appealOpen`,
  `finishExpired`, `quota`, `admitted`, `storageAvailable`, `answerBlankCount`,
  `taskCardCount`, `lateSubmissionAllowed`, `appealsAllowed`, `modifiersAllowed`,
  `taskCardsShared`, `templateKey`, `templateHeading` создаёт изолированные
  игру, две команды, три задачи, восемь QR и восемь уже принятых ответов-заготовок.
- `PATCH /__test/scenarios/{gameId}` обновляет только внешние условия этого сценария.
- `PATCH /__test/receipts/{receiptId}` с `admissionVersion`, `acceptedAt` задаёт
  время/версию готовой квитанции для сценария поздней доставки; идентичность и
  привязка задачи не изменяются. Это настройка заглушки, не API приёма.
- `POST /__test/clock/advance` `{milliseconds}` продвигает часы стенда для проверки
  истечения назначений. Будущий сервис в тестовом режиме использует эти часы;
  production использует собственные серверные часы, не управляющий HTTP endpoint.
- `POST /__test/alternative-tasks` `{taskId,referenceAnswer}` создаёт независимую
  задачу-заготовку с новым ID; исходная задача и назначения игры не меняются.
  Это только подготовка данных внешней библиотеки, не реализация её редактора.
- `GET /__test/events?gameId=...` возвращает сообщения, принятые стендом.
- `GET /__test/images?gameId=...` возвращает сохранённые изображения.
- `PUT /__test/event-sink` `{available}` включает/выключает приём сообщений.

Дедлайны вычисляются относительно управляемого времени создания сценария.
PATCH меняет конкретный дедлайн только при явном изменении соответствующего
параметра; lateSubmissionAllowed не сдвигает сроки апелляций. Открытые сроки —
через час, закрытые — час назад. Это не значения production-настроек.
Для тестирования задержанной доставки у заготовок `acceptedAt` лежит до дедлайна.
Строка `fixture-signed:<UUID>` имитирует результат проверки подлинности QR, но не
предлагается как способ подписи реального QR.

## Данные редакции 0.2

Бланк и квитанция содержат taskId/taskNumber до проверки. Первые два бланка
каждой команды относятся к одной задаче для теста запрета повторной апелляции.
Эталоны задач различаются. `quota` — только параметр подготовки теста:
в GET /games лимита нет, его устанавливает сервис проверки.

Изменение submissionOpen/lateSubmissionAllowed увеличивает admissionVersion,
но не создаёт игру и не сбрасывает ответы/квоту/бланки. Закрытие по дедлайну в
реальной системе тоже обновляет версию режима приёма.

Неизвестный ранее system не требует изменения ядра сервисов. Его capabilities
и templateKey заданы данными. Для новых профилей возможности по умолчанию выключены.

Тестовый формат declarative-v1 содержит answerSheet/taskSheet — последовательности
блоков field (heading/taskNumber/statement), qr и answer-area. Печатная проекция
не содержит referenceAnswer; произвольный JS и доступ к серверным объектам
не разрешены. Сложные макеты добавляются через версию формата/адаптер рендерера,
а не через ветвление по названию игры.

## Снимки и назначения (редакция 0.3)

scenario.blankImages содержит PNG с настоящим QR для каждого qrTokens[index].
invalidQrImage содержит читаемый, но незарегистрированный invalidQrToken.
Это синтетические снимки для проверки транспорта/декодирования, не макеты бланков.
Минимальная pngBase64 без QR теперь используется только в отрицательных тестах.
В приёме нужен настоящий серверный декодер; заглушки декодирования нет.
Самопроверка стенда независимо считывает созданные QR через jsQR.

Для тестов проверки настройте небольшой положительный TTL (например 60 секунд)
и адаптер часов GET /clock. Точная production-длительность не зафиксирована ТЗ.
POST /__test/clock/advance управляет только временем заглушки, не самим сервисом.
Тесты вычисляют сдвиг по lease.expiresAt. Assignment-Token — технический заголовок
временного назначения, UI передаёт его без дополнительного действия проверяющего.
