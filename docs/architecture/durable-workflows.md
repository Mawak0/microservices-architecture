# Сохранённые команды и саги

Изменяющий запрос после проверки пользователя, роли и JSON записывается в PostgreSQL **до выполнения обработчика**. Сага не объединяет три независимых сервиса в один общий процесс. Выпуск материалов, подготовка PDF, сдача ответа и ручная проверка имеют свои контрольные точки.

## Участники и контрольные точки

| Процесс | Шаги | Контрольная точка | Отказ и компенсация |
| --- | --- | --- | --- |
| Выпуск бланков/комплекта | Сохранённая команда → локальная транзакция материалов: бланки, комплект, результат повторяемой команды, outbox | Локальная транзакция зафиксирована | При предметном отказе транзакция откатывается. Выпущенные идентификаторы после успешной фиксации не отменяются |
| Подготовка PDF | Сохранённая команда → задание печати со снимком данных → назначенный обработчик → закрытый объект S3 → транзакция метаданных и готовности → сверка состояния | `PdfReady`: готовое задание и метаданные PDF присутствуют в PostgreSQL | Ошибка шаблона даёт окончательный отказ; недоступность S3 оставляет задание для восстановления. Лишний объект старого обработчика не становится действующим артефактом |
| Сдача ответа | Сохранённая команда → повторное чтение QR и проверка допуска → резервирование → S3 → транзакция принятого ответа, идемпотентного результата и outbox → доставка события в проверку → транзакция проверки и inbox → подтверждение источнику | `ReviewRegistered`: ответ зафиксирован в сервисе проверки | До принятия резервирование снимается и в outbox сохраняется удаление загруженного объекта. Удаление повторяется. После принятия ответ необратим: недоступность проверки вызывает повторную доставку, а не удаление ответа |
| Вердикт/апелляция/квота/завершение | Сохранённая пользовательская команда → локальная транзакция проверки: агрегаты, результат команды и outbox | Локальная транзакция зафиксирована | Предметные ограничения дают окончательный отказ. Публикация событий восстанавливается отдельным существующим outbox; вердикт и списание/возврат квоты повторно не выполняются |

Получение снимка, эталона, настроек игры и другие чтения не создают сагу. `POST /blank-verifications` также является чтением. Входящие `/integrations/*` уже защищены исходящим outbox и атомарным inbox получателя: они отвечают только после фактической фиксации, а не после помещения в ещё одну очередь.

## Идентичность и подтверждение

`processes` хранит идентификатор операции, версию процесса (1), пользователя и снимок его разрешённых ролей, область команды, ключ идемпотентности, отпечаток параметров, аргументы, состояние, число попыток, следующий запуск, fenced lease, ожидаемую контрольную точку и итог. Bearer-токен не сохраняется. Повторное выполнение восстанавливает уже разрешённую команду; это техническое продолжение исходного действия. Новые команды снова проходят авторизацию.

В `ReceiptAccepted` сохраняются `operationId` и `processVersion`; они проходят через резервирование и outbox и не теряются при перезапуске. Сервис проверки возвращает `Operation-Id`, `Process-Version`, `Checkpoint: ReviewRegistered` **после** транзакции проверки/inbox. Источник сверяет эти поля, идентификаторы ответа, бланка, задачи и игры, затем сохраняет контрольную точку и только после этого помечает исходящее сообщение доставленным. Ответ с другим идентификатором, версией или неполными данными не подтверждает цепочку.

Если подтверждение пришло до записи результата исходного HTTP-обработчика, оно сохраняется в `process_checkpoints`. Завершение попытки сверяется с этой записью в своей транзакции. Потеря подтверждения после фиксации у получателя приводит к повтору того же события с тем же `eventId` и ключом идемпотентности: inbox возвращает ранее сохранённую проверку, включая повторное подтверждение.

Печать сверяет долговременное состояние задания и метаданные артефакта, а не сообщение из памяти. Перезапуск между фиксацией PDF и подтверждением восстанавливается `PrintCheckpointProbe`.

## Повторы и исходы

Состояния: `Accepted → Running → Completed` либо `AwaitingCheckpoint → Running` при истечении ожидания. Окончательный отказ: `Failed`; требуемое удаление внешнего объекта: `Compensating → Failed`. Временный отказ компенсации оставляет её активной. Ошибка хранения или сетевой тайм-аут не доказывает, что получатель ничего не сделал.

Один обработчик владеет командой до `lease_until`; SQL `FOR UPDATE SKIP LOCKED` распределяет работу между экземплярами. Результат фиксируется только при действующем токене назначения. Запись старого обработчика после истечения срока игнорируется. Идемпотентность предметного обработчика защищает эффекты даже при потере lease во время внешнего вызова.

По умолчанию: lease 60 секунд, попытка HTTP ограничена 80% lease, ожидание контрольной точки 30 секунд, повтор от 1 секунды до 2 минут с небольшим случайным разбросом. После 10 попыток пишется предупреждение; повторы продолжаются без предельного числа попыток. `Workflows:LeaseSeconds`, `Workflows:CheckpointTimeoutSeconds`, `Workflows:RetryBaseMilliseconds` задаются конфигурацией.

Только окончательный переход удаляет аргументы сохранённого запроса. Идентичность, отпечаток, итог и `process_history` сохраняются для поздних повторов и диагностики. Принятый до дедлайна ответ при технической повторной доставке остаётся тем же ответом; сроки игры не запускают новый цикл.

## HTTP

Ответы содержат `Operation-Id`, `Operation-Status`, `Operation-Location`. `202` с представлением операции означает, что запрос долговременно принят и выполнение ещё ожидается. Прежние ответы с предметным результатом сохраняются, но `AwaitingCheckpoint` явно показывает, что цепочка ещё не закончена. Задание печати само по себе также возвращает `202` с его идентификатором.

`GET /operations/{id}` возвращает статус, версию, число попыток, следующую попытку, код последнего отказа и идентификатор результата. Доступ имеют владелец и администратор; чужая операция даёт 404. Исходные аргументы, роли, заголовки и фото в этом API не выдаются. Тот же ключ с другими параметрами даёт 409.

`Workflows:Enabled=false` оставлен для изолированной проверки прежних HTTP-контрактов. В рабочем запуске механизм включён по умолчанию. Старые приёмочные сценарии проверяют исходные бизнес-правила отдельно; новые HTTP-тесты запускают механизм целиком.

## Направление зависимостей и проверка

`Olympiad.Workflows.Domain` содержит переходы процесса без PostgreSQL, HTTP и часов. `Application` определяет порты и координатор. `Infrastructure` реализует PostgreSQL, HTTP, расписание и фонового обработчика. Каждый сервис использует собственную базу; таблицы другого сервиса не читаются. Composition root связывает общий механизм с ролями, ошибками и контрольными точками сервиса.

`tests/Olympiad.Workflows.Tests` проверяет конкуренцию, потерю подтверждения после эффекта, новый экземпляр приложения, истечение назначения, раннее/позднее подтверждение, контроль версии, отсутствие повторного эффекта, компенсацию и доступ к состоянию. Тесты сервисов дополнительно проверяют настоящие обработчики при включённых workflow, подтверждение проверки и сверку печати, а также удаление только принадлежащих отклонённой загрузке объектов в настоящем S3.
