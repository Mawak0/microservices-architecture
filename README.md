# Sapientum: contract-first задание

В этой ветке находятся контракт и исполняемые требования **одного** сервиса.
Реализации сервиса, базы данных, бизнес-логики и HTTP-обработчиков здесь нет.
Язык будущей реализации не ограничен. Тестовый клиент использует Node.js 22+
и встроенный `node:test`; Ajv проверяет JSON Schema, ответы API и события.
Зависимости тестов зафиксированы в package-lock.json.

## Документы

- `SERVICE.md` — границы конкретного сервиса, сценарии и ограничения покрытия.
- `contracts/openapi.json` — предлагаемый HTTP API, OpenAPI 3.1.
- `contracts/common.json` — общие схемы.
- `contracts/events.schema.json` — исходящие события, JSON Schema 2020-12.
- `contracts/requirements.md` — связь требований с приёмочными тестами.
- `CONTRACTS.md` — общие договорённости и отличия требований от проектных решений.
- `test-support/README.md` — контракт тестовых соседних систем.

## Проверка документов и тестового стенда

```sh
npm ci
npm test
```

Это проверка JSON Schema, локальных `$ref`, структуры API и работы **заглушек**.
Зелёный результат **не означает**, что сервис реализован или прошёл требования.
Дополнительная проверка OpenAPI стандартным валидатором:

```sh
npm exec --yes --package=@redocly/cli@2.62.1 -- redocly lint contracts/openapi.json --extends minimal
```

## Запуск приёмочных тестов после появления реализации

1. Запустить `npm run fixtures` в отдельном терминале (по умолчанию порт 19100).
2. Запустить реализацию сервиса с адаптерами соседних систем, направленными на
   `http://127.0.0.1:19100`, согласно `test-support/README.md`.
3. Указать URL **отдельного тестового** экземпляра сервиса и разрешить запись:

```powershell
$env:SERVICE_BASE_URL = 'http://127.0.0.1:8080'
$env:CONTRACT_TEST_ALLOW_WRITES = '1'
npm run test:acceptance
```

Без URL и явного разрешения записи тесты завершаются ошибкой, не пропускаются.
Сейчас сервиса нет: приёмочный набор намеренно не может быть зелёным.
Каждый тест создаёт изолированный сценарий с новыми UUID; очищать чужие данные
тесты не пытаются. Не запускайте их против production.

Дополнительно: `FIXTURE_BASE_URL` — адрес заглушек; `TEST_TIMEOUT_MS` — время
ожидания асинхронного результата (по умолчанию 10000 мс).

## Ветки

- `contracts/materials-service` — бланки и печатные материалы.
- `contracts/intake-service` — приём ответов.
- `contracts/review-service` — проверка и апелляции.

Ветки имеют общий инфраструктурный базовый коммит, но каждая содержит контракт
только своего сервиса. Это альтернативные рабочие ветки, а не три последовательных
коммита одной реализации. Для объединения сервисов позже потребуется согласовать
структуру каталогов и интеграционные адаптеры.
