# Архитектура сервиса проверки

Зависимости проектов направлены внутрь:

```text
Api → Application → Domain
Api → Infrastructure → Application / Domain
```

Domain использует только BCL. Application не знает SQL, HTTP, JSON, DI, filesystem
или ASP.NET Core. Infrastructure implements capability-specific Application ports.
Api импортирует Infrastructure только в Program.cs, месте сборки графа зависимостей.
Фоновые HTTP-host классы зависят от Application, делегируя вычисление полноты ему.

## Разделение ответственности

AnswerCheck владеет исходным и текущим вердиктами, историей и временным назначением.
Токены старых назначений сохраняются вместе с агрегатом и не возрождаются после
повторного claim, даже если исполнитель прежний. Истёкшие назначения возвращаются
в очередь при следующем чтении/получении работы. Отдельные методы агрегата защищают
сохранение результата, продление и освобождение. Административная коррекция
аннулирует назначение; открытая апелляция сохраняется в очереди до явного решения.

Appeal представляет единственное обжалование teamId + gameId + taskId.
GameAppealQuota хранит единый расход всей игры. Признанная ошибка требует
фактического изменения вердикта; решение апелляции, история, возврат квоты и
соответствующие события сохраняются в одной транзакции. Повторное решение
запрещено, возвращённая квота не снимает уникальность обжалованного задания.

GameReviewCompletion требует актуальный накопительный manifest, наличие каждого
ответа и отсутствие непроверенных ответов/апелляций. Разрешённая поздняя сдача
или окно допустимых апелляций блокирует завершение. Новая версия приёма инвалидирует
старый manifest, сохраняя дела и квоту. CompletionRefresh регулярно обновляет
зарегистрированные игры; события появляются после финального вердикта или
истечения срока без HTTP-поллинга со стороны пользователя.

ReceiptAccepted сверяется с доверенным сервисом приёма. Эталон читается один раз
по точному taskId и сохраняется неизменяемым с делом. Новые задачи не подменяют
старые. Обработка дубликата существующего дела не вызывает внешние зависимости
и не переписывает идентичность или эталон.

## SOLID в конкретных решениях

SRP: отдельные сценарии получения, назначения, выдачи/коррекции вердикта, подачи
и разрешения апелляции, квот и полноты. Repositories отражают агрегаты;
HTTP-адаптеры отражают соседние системы. Нет общего диспетчера бизнес-команд.

OCP: правила используют capabilities и сроки игры, а не её имя. Изменение профиля
новой игры не меняет Domain. HTTP и SQLite могут заменяться адаптерами портов.

LSP: xUnit проверяет тот же RecordVerdict через память и через SQLite, включая
идемпотентность. Доменные инварианты принадлежат агрегатам, а не SQL-адаптеру.

ISP: IClock, ITaskAnswers, IGameProfiles, IAcceptedReceipts, IIdentityProvider,
IEventPublisher и репозитории небольшие и имеют конкретное назначение.
IReviewSession объединяет согласованные репозитории только внутри одной
транзакции, а не предоставляет универсальный CRUD или service locator.

DIP: сценарии получают порты конструктором. SQL/HTTP реализуют эти порты;
Program связывает конкретные адаптеры. Domain и Application не ссылаются на них.
Тесты проверяют фактические зависимости сборок, csproj, исходники и инкапсуляцию.

## Согласованность и восстановление

SQLite BEGIN IMMEDIATE резервирует запись на уровне базы, а не процесса.
Уникальные ограничения дополнительно защищают receiptId и team-game-task.
Сохранение агрегатов, истории, квоты, исходящих событий и успешного ответа
идемпотентности атомарно. Неуспешная команда откатывается целиком.

Idempotency scope: actor + HTTP method/path + key. Fingerprint учитывает тело
запроса и Assignment-Token. Авторизация предшествует повтору; повтор успешной
команды считывается до обращения к изменяемым внешним условиям, включая часы.
Поэтому истечение назначения или отключение зависимостей не меняет уже
зафиксированный ответ. Внутри транзакции выполняется вторичная проверка ключа,
защищающая два одновременных одинаковых запроса.

Outbox хранится в той же SQLite. Публикация как минимум однократная; после сбоя
или перезапуска сообщение отправляется с тем же eventId. Сетевые вызовы
бизнес-зависимостей выполняются до SQL-транзакций. Background publication вызывает
порт транспорта и отмечает доставку после успешного ответа.

Снимки агрегатов — типизированные внутренние модели; JSON-сериализация находится
только во внешнем адаптере хранения. Изменяемые коллекции входных/выходных снимков
копируются; свойства состояния агрегатов не имеют публичных setter.

## Проверки и эксплуатационные границы

21 xUnit test: бизнес-инварианты, подстановка портов, конкурентный расход общей
квоты через разные соединения, rollback состояния+outbox, SQL uniqueness,
восстановление успешного ответа/назначения, повторная доставка после отказа.
46 исходных приёмочных сценариев и два runtime-сценария выполняются через
отдельный реальный HTTP-процесс с новой SQLite, не через заглушку сервиса.

Для эксплуатации нужно настроить реальные identity/game/task/receipt/event
провайдеры и credential, резервное копирование SQLite, TLS и доступ к техническим
маршрутам на уровне инфраструктуры. Библиотека сохраняет старые taskId и запрет
замены задач во время игры. Владелец игры сверяет версию завершения: локальная SQL
транзакция не может заблокировать изменение игры в чужом сервисе.

SQLite подходит одному локальному persistent volume; масштабирование на разные
узлы потребует замены реляционного адаптера/механизма публикации, не переписывания
доменной модели. Политики архивирования журнала/idempotency, ретеншн данных и
мониторинг lag outbox выбираются для реального развёртывания.
