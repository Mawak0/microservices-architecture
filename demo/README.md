# Живой стенд трёх сервисов

Адрес: **http://127.0.0.1:19180**. Материалы, приём и проверка — настоящие .NET-приложения. Каждое подключается к собственной PostgreSQL-базе и роли. Фотографии находятся в закрытом S3-бакете `answer-images`, PDF — в `print-materials`. Сохранённые команды и исходящие события переживают перезапуск.

## Запуск

С Docker: заполните `deploy/.env` по примеру `deploy/.env.example`, затем из корня:

```sh
docker compose -f deploy/compose.yml --env-file deploy/.env up -d --build --wait
```

На Windows без Docker, с установленными .NET SDK 8, Node.js 22, PostgreSQL 17 и официальным VersityGW 1.11.0:

```powershell
powershell -NoProfile -File demo/Start.ps1 -NoBrowser -VersityExe C:/tools/versitygw/versitygw.exe
```

На подготовленном компьютере параметр `-VersityExe` можно опустить: используется проверенный исполняемый файл из `.local/versitygw/`. Скрипт создаёт отдельный кластер PostgreSQL на **55433**, VersityGW на **17071**, случайные локальные пароли и четыре базы/роли (`materials`, `intake`, `review`, `demo`), каждая со своим паролем. Используется SCRAM и привязка к loopback. Имеющийся системный PostgreSQL не изменяется. Локальные данные, конфигурация и журналы находятся в игнорируемом `.demo-data/`.

API: материалы — 19181, приём — 19182, проверка — 19183. Во внешнем Compose-профиле PostgreSQL/S3 доступны на 55432/17070. Все опубликованные порты привязаны к 127.0.0.1.

`demo/Stop.ps1` проверяет принадлежность PID и останавливает локальные процессы с сохранением данных; `-KeepStorage` оставляет PostgreSQL и S3 включёнными. Compose останавливается командой `docker compose -f deploy/compose.yml --env-file deploy/.env stop`; следующий запуск сохраняет тома. Томы удалять для перезапуска не требуется.

## Сценарий показа

1. Создайте игру «Бонусы». Администратор готовит комплект и дополнительный бланк с модификатором +3.
2. Наблюдатель запрашивает PDF. Документ создаёт настоящий фоновый обработчик, сохраняет его в S3 и подтверждает контрольную точку `PdfReady`.
3. Подготовьте снимок с ответом 5 или загрузите фотографию. Браузер читает QR; сервис приёма повторно распознаёт его и проверяет подпись через сервис материалов. Без читаемости и при поддельном QR сдача отклоняется.
4. Сдайте бланк. После сохранения фотографии и принятого ответа событие из outbox поступает напрямую в проверку. После фиксации проверки/inbox источник получает совпадающее подтверждение `ReviewRegistered`. Повторная сдача того же бланка запрещена.
5. Проверяющий берёт ответ, видит снимок и эталон и сохраняет «Неправильно».
6. Наблюдатель подаёт апелляцию, проверяющий исправляет ошибку жюри. История и исходный вердикт сохраняются, квота возвращается один раз. Повторная апелляция запрещена; в «Домино» апелляций нет.
7. Истечение дедлайнов не завершает игру, пока есть проверки или апелляции. Повторное открытие разрешает позднюю сдачу без удаления истории.

Счётчики в рабочем месте показывают доступные первичные ответы и апелляции. На вкладке событий видны реальные публикации материалов/проверки и HTTP-вызовы; передача принятого ответа идёт напрямую между API.

## Проверки

```sh
node demo/smoke.mjs
node demo/restart-smoke.mjs before
# Остановите и снова запустите стенд без удаления данных.
node demo/restart-smoke.mjs after
```

Первый сценарий выполняет 21 предметную проверку. Проверка перезапуска сравнивает идентичность игры, бланка, принятого ответа и проверки, а также SHA-256 полученных через API фотографии и PDF. Она прошла на локальном стенде после остановки и запуска всех процессов, включая PostgreSQL и S3. CI дополнительно собирает и запускает полный Compose и повторяет эти проверки.

Пользователей, турнир и задачи предоставляет демонстрационный адаптер Node.js; его данные тоже в отдельной базе PostgreSQL. Переключение ролей намеренно упрощено для показа. Этот адаптер не является рабочей системой аутентификации; сервисы сохраняют собственные проверки прав и закрытый доступ к файлам. Постоянных копий фото в Base64/JSON или PDF на диске адаптера нет. `.demo-data/demo-print.pdf` — только явно выгруженный тестом документ для визуальной проверки.

`node demo/storage-isolation.mjs` проверяет независимые пароли, запрет доступа к чужой базе и анонимного доступа к бакетам. Для Compose используется `--compose`. `demo/delivery-smoke.mjs prepare|submit|verify` проверяет сохранение принятого ответа при недоступной проверке и ровно одну доставку после восстановления; CI останавливает проверку между prepare и submit и затем перезапускает весь стенд.
