# PostgreSQL, S3 и три сервиса

Скопируйте `.env.example` в `.env` и задайте локальные пароли. Из этого каталога выполните `docker compose --env-file .env up -d --wait`. Compose также собирает три API и демонстрационный адаптер, доступный на http://127.0.0.1:19180. PostgreSQL 17.6 хранит данные в постоянном томе; три сервиса используют отдельные базы и роли `materials`, `intake`, `review`. Эти роли не имеют доступа к базам других сервисов.

API требует `Storage__ConnectionString`, например `Host=127.0.0.1;Port=55432;Database=intake;Username=intake;Password=...`. Отсутствующая или SQLite-строка подключения завершает запуск ошибкой. Параметры HTTP-зависимостей описаны в README сервисов. Начальная схема создаётся идемпотентно из `PersistenceSchema.sql` соответствующего Infrastructure-проекта. Перенос старых баз не выполняется.

Все локальные транзакции работают с уровнем SERIALIZABLE. Ошибки сериализации и взаимной блокировки повторяют только локальную транзакцию с ограничением числа попыток; сетевые эффекты внутри неё запрещены. Ограничения UNIQUE защищают идентичность бланка, ответа и апелляции. Начальная схема сериализуется advisory-lock только на время создания; обычные запросы не удерживают глобальную блокировку.

Для тестов используйте отдельную PostgreSQL-базу и задайте `TEST_POSTGRES_CONNECTION`. Учётная запись тестов должна иметь право создания схем. Каждый тестовый экземпляр получает отдельную схему; повторный запуск того же экземпляра использует её же, проверяя долговечность данных. Тестовая БД одноразовая и не должна содержать данные приложения. Команды: `npm ci --prefix services/<service>`, затем `node tools/review-ci.mjs <service>` для `materials`, `intake`, `review`. CI поднимает настоящий PostgreSQL, включая тесты HTTP и перезапуска.

Резервная копия: `pg_dump --format=custom --dbname="$CONNECTION_STRING" --file=service.dump`. Восстановление в пустую базу: `pg_restore --exit-on-error --dbname="$CONNECTION_STRING" service.dump`. Копировать нужно все три базы; ключ подписи QR хранится в базе материалов и входит в её копию. Проверяйте восстановление на отдельном экземпляре. `docker compose stop` сохраняет том, `docker compose start` запускает его повторно.


# S3: фотографии и PDF

VersityGW 1.11.0 запускается тем же Compose-файлом с постоянным томом `s3-data` и `fsync` для подтверждения записи на диск. Задайте `S3_ACCESS_KEY` и `S3_SECRET_KEY` в `.env`. Для API материалов и приёма нужны `S3__Endpoint` (локально `http://127.0.0.1:17070`), `S3__Region=us-east-1`, `S3__AccessKey`, `S3__SecretKey`. Сервисы создают свои закрытые бакеты `print-materials` и `answer-images`; конфигурация отсутствующего хранилища завершает запуск ошибкой. Другой S3-сервер подключается этими настройками.

Ключ объекта зависит от владельца и SHA-256 содержимого; загрузка условная, без перезаписи существующего объекта. PDF дополнительно связан с токеном обработчика. В PostgreSQL находятся ключ, MIME-тип, размер и SHA-256, а не постоянные копии файлов. Временные байты незавершённой сдачи сохраняются до её восстановления и удаляются при завершении; принятый снимок в БД не дублируется. Загрузка S3 выполняется вне транзакции PostgreSQL. Состояние готовности PDF, ссылка и событие фиксируются в одной локальной транзакции только после успешной загрузки. Проверка владения назначением не позволяет устаревшему обработчику привязать свой PDF.

Снимок выдаёт `GET /receipts/{id}/image` после проверки роли; PDF — `GET /print-jobs/{id}/artifact`. Ссылки указывают на API, без credentials и публичного доступа к бакету. Чтение проверяет размер, тип и SHA-256 по зафиксированным метаданным.

В тестах дополнительно задаются `TEST_S3_ENDPOINT`, `TEST_S3_ACCESS_KEY`, `TEST_S3_SECRET_KEY`. Материалы проходят полную HTTP-приёмку с настоящим VersityGW. Тесты S3 проверяют потерю подтверждения записи, дубликат, отсутствие перезаписи, перезапуск клиента, закрытый доступ, повреждение метаданных, контрольную сумму и отмену. Отдельная проверка приёма сохраняет снимок в реальном S3 и получает его после пересоздания адаптеров PostgreSQL/S3. Старый HTTP-адаптер изображений используется только в среде контрактных тестов для воспроизведения ошибок внешнего хранения; рабочая среда использует S3.

Резервируйте том `s3-data` согласованно с базами при остановленных сервисах; восстановление должно включать данные и метаданные VersityGW. Копия только PostgreSQL не содержит фотографий или PDF. Перенос прежних SQLite/JSON/Base64-хранилищ отсутствует.


# Проверка невостребованных объектов

Остановите **все экземпляры** соответствующего API и фоновых обработчиков, оставив PostgreSQL и S3 доступными. Утилита использует только базу этого сервиса и его бакет; действующие метаданные, временные сдачи и объекты текущих назначений печати защищены. По умолчанию рассматриваются только объекты старше 24 часов, и выполняется только просмотр.

Задайте `MAINTENANCE_CONNECTION_STRING`, `S3_ENDPOINT`, `S3_ACCESS_KEY`, `S3_SECRET_KEY` и при необходимости `S3_REGION`:

```sh
dotnet run --project tools/Olympiad.Storage.Maintenance -- materials
dotnet run --project tools/Olympiad.Storage.Maintenance -- intake
# После проверки плана, при остановленных экземплярах:
dotnet run --project tools/Olympiad.Storage.Maintenance -- materials --apply --services-stopped
dotnet run --project tools/Olympiad.Storage.Maintenance -- intake --apply --services-stopped
```

Утилита дополнительно отказывается удалять объекты, если в базе есть другие соединения той же роли. Флаг `--services-stopped` фиксирует обязательное условие обслуживания; одновременно запускать API нельзя. `MAINTENANCE_MINIMUM_AGE_HOURS` меняет период защиты. Повторный запуск безопасен после частичного сбоя удаления. Снимки принятых ответов и привязанные PDF не удаляются; техническая компенсация отклонённой загрузки также работает автоматически через outbox.

Общая схема процессов и контрольных точек: [durable-workflows.md](../docs/architecture/durable-workflows.md). Команды, роли, сценарий живой демонстрации и проверка перезапуска: [demo/README.md](../demo/README.md).
